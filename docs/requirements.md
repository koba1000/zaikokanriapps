# 要件定義書：喫茶店 在庫管理アプリ

版: 0.1（ドラフト） / 作成日: 2026-11-02

## 1. 背景・目的
喫茶店の在庫管理に関する顧客要望に応える。
- 毎朝の在庫把握を素早く行えるようにする
- 発注（注文）作業を楽にする
- 予算は「できるだけ安く」、安全性は「できるだけ安全」

## 2. スコープ
### 2.1 対象
- 在庫の登録・更新・閲覧、毎朝の在庫確認ダッシュボード
- 発注点（閾値）割れの検知と発注候補リスト、発注記録
- 従業員アカウント管理、ログイン
- 従業員情報（住所を含む）の管理（店長のみ）
- 売上の登録・閲覧（店長のみ）

### 2.2 対象外（今回）
- VPN／閉域網（採用しない。代わりに HTTPS＋認証＋多層防御で担保）
- 仕入先への自動発注連携、POS連携、決済
- ネイティブアプリ（スマホブラウザ対応のレスポンシブWebのみ）

## 3. 利用者・ロール
| ロール | 人数目安 | 権限 |
|---|---|---|
| 店長（owner） | 1 | 全機能。従業員管理・売上・住所の閲覧/編集 |
| スタッフ（staff） | 5程度 | 在庫の閲覧/更新、発注候補の閲覧。売上・従業員住所は不可 |

最小権限の原則（RBAC）。権限判定はサーバー側で必ず行う。

## 4. 技術構成（確定）
| 層 | 採用 | 備考 |
|---|---|---|
| フロント | Flask + Jinja2（SSR）、最小限のJS | SPAを避け攻撃面とコストを削減（Q1参照） |
| アプリサーバー | Render（Web Service）, Flask, Gunicorn | HTTPSはRender標準 |
| DB | Neon（PostgreSQL） | TLS必須（sslmode=require）、アプリ専用ロール |
| CI/CD | GitHub Actions | Renderはmainへのマージで自動デプロイ（CI成功を条件） |
| AI開発 | GitHub Copilot | 指示ファイル・ガードレールで制御 |
| ネットワーク | VPNなし | 公開インターネット経由。IP制限は行わない |

## 5. 扱う情報と分類
| 情報 | 分類 | 主な保護策 |
|---|---|---|
| 在庫データ | 低〜中 | 認証必須、監査ログ |
| ログイン情報（ID/パスワード/セッション） | 高 | Argon2id等でハッシュ化、平文保存禁止、ログ出力禁止、セッション保護 |
| 従業員の住所 | 高（個人情報） | 店長のみ閲覧、アプリ層で暗号化（列暗号化）、閲覧の監査ログ、最小収集 |
| 店の売上 | 中〜高 | 店長のみ、監査ログ |

## 6. 機能要件
| ID | 要件 | 優先度 |
|---|---|---|
| F-01 | IDとパスワードでログイン／ログアウトできる | 必須 |
| F-02 | 品目（名称・単位・現在庫・発注点・仕入先・標準発注量）のCRUD | 必須 |
| F-03 | 毎朝の在庫画面：全品目の現在庫を一覧し、発注点割れを強調表示 | 必須 |
| F-04 | 在庫数量の更新（棚卸入力）。更新履歴（誰が・いつ・変更前後）を保存 | 必須 |
| F-05 | 発注候補リスト自動生成（発注点割れ品目×標準発注量）と、発注済み記録 | 必須 |
| F-06 | 発注候補を仕入先別にテキスト/CSVでコピー・出力（CSV実装済み・TDD） | 推奨 |
| F-07 | 従業員アカウントの作成・無効化・ロール変更（店長のみ） | 必須 |
| F-08 | 従業員情報（住所等）の登録・閲覧（店長のみ） | 必須 |
| F-09 | 売上の日次登録・期間別閲覧（店長のみ） | 必須 |
| F-10 | 監査ログの閲覧（店長のみ） | 推奨 |
| F-11 | パスワード変更。初期パスワードは初回ログイン時に変更を強制 | 必須 |

## 7. 非機能要件
### 7.1 セキュリティ
| ID | 要件 |
|---|---|
| S-01 | 全通信HTTPS。HSTS、セキュアCookie（Secure/HttpOnly/SameSite=Lax）を設定 |
| S-02 | パスワードはArgon2idまたはbcryptでハッシュ化。最小長12文字、弱PW拒否 |
| S-03 | ログイン試行のレート制限・一時ロックアウト。エラーメッセージでアカウント存在有無を漏らさない |
| S-04 | CSRF対策を全状態変更リクエストに適用 |
| S-05 | SQLはORM/プレースホルダのみ（文字列連結禁止）。Jinja2自動エスケープを無効化しない |
| S-06 | 全エンドポイントで認証・認可（RBAC）をサーバー側で強制。デフォルト拒否 |
| S-07 | セキュリティヘッダ（CSP、X-Content-Type-Options、frame-ancestors、Referrer-Policy） |
| S-08 | 秘密情報（DB接続文字列、SECRET_KEY、暗号鍵）はRender環境変数で管理し、リポジトリに含めない |
| S-09 | 従業員住所はアプリ層で暗号化して保存。鍵はDBと別管理 |
| S-10 | DBアプリ用ロールは最小権限（DDL不可）。マイグレーション用ロールは分離 |
| S-11 | 依存パッケージの脆弱性を継続検査（CIで失敗させる） |
| S-12 | 重要操作（ログイン、権限変更、住所閲覧、売上閲覧、在庫更新）を監査ログに記録。個人情報・秘密情報はログに出さない |
| S-13 | セッション有効期限（アイドル30分、絶対12時間）。パスワード変更時に全セッション失効 |
| S-14 | 店長アカウントにはMFA（TOTP）を推奨（フェーズ2） |

### 7.2 可用性・バックアップ
- 営業時間（朝〜夕）に利用可能。目標稼働率 99%（ベストエフォート）
- Neonのポイントインタイムリストアを活用。復旧手順を文書化し、四半期に1回リストア確認
- RPO 24時間以内、RTO 4時間以内（目安）

### 7.3 コスト
- 月額できるだけ低コスト。まず Render・Neon の無料/最安プランで開始
- 注意：Render無料プランはスリープ（初回遅延）があり、朝の利用に影響し得る（Q2）
- 追加の有料SaaSは原則使わない（CI解析はGitHub標準/OSSを優先）

### 7.4 性能・運用性・保守性
- 同時利用 5〜6名。主要画面の表示 2秒以内（スリープ復帰時を除く）
- スマホで操作可能なレスポンシブUI、日本語UI
- 構造化ログ、保持期間 90日
- テストカバレッジ目標：ビジネスロジック 80%以上、認可ロジックは全分岐を検証

### 7.5 法令・個人情報
- 従業員住所は個人情報。利用目的を限定し、取扱者を店長に限定
- 退職者情報の削除/匿名化方針を定める

## 8. AI駆動開発・CI/CD要件
詳細は [defense-in-depth.md](./defense-in-depth.md) と [ai-development-rules.md](./ai-development-rules.md)。

| ID | 要件 |
|---|---|
| D-01 | main直接pushを禁止し、PR＋必須ステータスチェック＋レビュー承認でのみマージ |
| D-02 | AI生成コードも人間コードと同一のCIゲートを通す |
| D-03 | CIにリンタ、型検査、テスト、SAST、依存/シークレットスキャン、設定検査を含める |
| D-04 | AIへの指示ファイル（Copilot instructions）でセキュア開発規約を明示 |
| D-05 | 人間の承認が必須な領域（認証・認可・暗号・DB権限・CI設定・依存追加）をCODEOWNERSで固定 |
| D-06 | デプロイはCI成功後のみ。ロールバック手順を用意 |

## 9. 受け入れ基準（抜粋）
- スタッフでログインし、売上画面・従業員住所画面に直接URLでアクセスしても403となる
- 発注点割れ品目が朝の在庫画面で強調され、発注候補に出る
- 従業員住所がDB上で平文で確認できない
- CIで高/重大の脆弱性・シークレット検出時にマージがブロックされる
- リポジトリ履歴に秘密情報が含まれない
